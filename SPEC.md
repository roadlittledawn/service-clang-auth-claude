# clang-auth — Specification

> **Status:** Draft v0.1 · 2026-11-05
> **Purpose:** A small, central authentication service shared by personal apps on subdomains of one root domain.
> **Experiment note:** Two independent implementations will be built from this spec using different harnesses and models. See [§14 Experiment Rules](#14-experiment-rules) before starting.

The words MUST, SHOULD, and MAY carry their RFC 2119 meanings. Anything not marked MUST is open to the implementer, who records the choice in `DECISIONS.md`.

---

## 1. Goals and Non-Goals

### Goals (MVP)
1. **One login for all my apps.** A user signs in once at `auth.{ROOT_DOMAIN}` and is signed in to every app on `*.{ROOT_DOMAIN}` they can access.
2. **Multiple users, access per app.** Each user has one identity (email + password) and is granted access, with roles, to specific apps.
3. **Invite-only registration.** There is no public sign-up. An admin creates a user, and the user sets a password through a one-time link.
4. **Admin through a CLI.** Apps, users, access grants, and sessions are managed with a command-line tool.
5. **Cheap to run.** About $0–2/month at personal-project scale.
6. **Easy to develop locally,** both for the service and for apps that use it, with no AWS account needed.

### Non-Goals (MVP)
- Acting as a full OAuth 2.0 / OpenID Connect provider (no authorization code flow, no client secrets, no discovery document).
- Social login (Google, GitHub, and so on).
- MFA/TOTP, passkeys, or WebAuthn. (Phase 2 candidate.)
- Sending email. Password resets are links generated by the admin and shared by hand.
- An admin web UI. (Phase 2, see §13.)
- Self-service sign-up.
- Apps outside `{ROOT_DOMAIN}`, which would need cross-domain SSO.
- Running in multiple regions, or high availability beyond what Lambda provides by default.

## 3. Core Concepts

- **User:** one person. Identified by email (unique, case-insensitive). Has a password and a status (`active` or `disabled`).
- **App:** a consuming application, identified by a slug (for example `recipes`). Has one or more allowed **origins** (for example `https://recipes.example.com`).
- **Grant:** a user's access to one app, with a list of free-form string **roles** (for example `["member"]` or `["admin"]`). A user with no grant for an app cannot use that app. The meaning of roles is decided by each app.
- **Session:** a long-lived login on the auth service, kept as an opaque random token in a cookie that only the auth host can read.
- **Access token:** a short-lived signed JWT in a cookie scoped to the parent domain. Apps verify it locally against JWKS without calling the auth service.
- **Invite:** a single-use, expiring token for setting a password. Used both for first-time setup and for admin-triggered resets.

## 4. Authentication Flow

### 4.1 Login (browser navigation)
1. An app finds no valid access token and redirects the browser to
   `https://auth.{ROOT_DOMAIN}/login?redirect_uri=<url-encoded app URL>`.
2. **If a valid session cookie already exists,** the service skips the form: it issues a fresh access token cookie and redirects to `redirect_uri` with a `302`.
3. **Otherwise** the service shows a minimal server-rendered HTML login form (email and password).
4. `POST /login` succeeds. The service then:
   - creates a session record and sets the **session cookie**,
   - sets the **access token cookie**,
   - redirects to `redirect_uri`.
5. **No access:** if `redirect_uri` belongs to app X and the user has no grant for X, the service shows a "You don't have access to X" page. The user is still logged in, and no redirect happens.

### 4.2 Validating `redirect_uri` (security-critical)
- It MUST be an absolute URL whose **origin exactly matches** a registered origin of an app (scheme, host, and port).
- `http://` is accepted only when `ALLOW_INSECURE_ORIGINS=true` (local dev).
- If it is missing or invalid, the service redirects to the auth service's own home page (`/`), which shows "Signed in as …" and a logout button. It MUST NOT redirect to an unregistered origin (no open redirects).

### 4.3 Refresh
- **Browser navigation:** this is the same as §4.1 step 2. Redirecting to `/login` with a valid session refreshes the access token without showing the form.
- **XHR/fetch:** `POST /api/session/refresh`, called cross-origin with `credentials: "include"`. If the session is valid, the response sets a new access token cookie and returns `200` with the claims as JSON. Otherwise it returns `401`. CORS MUST allow only registered app origins, with `Access-Control-Allow-Credentials: true`.
- A session MUST be rejected, and its cookies cleared, if the user is disabled or the session has expired or been revoked.

### 4.4 Logout
- `POST /logout`, from a form on the auth host or cross-origin from a registered origin. It deletes the session record, clears both cookies, and redirects to a validated `redirect_uri` or to `/`.
- A logout affects only the current session. Revoking all of a user's sessions is an admin operation (§8).
- An access token that was already issued stays valid until it expires, at most `ACCESS_TOKEN_TTL`. This is accepted for the MVP.

### 4.5 Password setup and reset (invite links)
- `GET /setup?token=…` shows a form for setting a password. `POST /setup` sets the password, marks the invite used, and logs the user in (as in §4.1 step 4, redirecting to `/`).
- Invites are single-use and expire after `INVITE_TTL` (default 72h). Each invite is stored as a SHA-256 hash, never in plain text.
- Creating a new invite for a user invalidates that user's earlier unused invites.
- Completing a reset MUST revoke all of the user's existing sessions.
- Password policy: at least 12 characters, at most 128. No composition rules.

## 5. Tokens and Cookies

### 5.1 Session cookie
| Attribute | Value |
|---|---|
| Name | `ca_session` |
| Value | 32+ bytes from a CSPRNG, base64url |
| Scope | Host-only (auth host), `Path=/` |
| Flags | `HttpOnly`, `Secure` (unless `COOKIE_SECURE=false`), `SameSite=Lax` |
| Lifetime | `SESSION_TTL` (default 30 days), extended on use (sliding) up to `SESSION_MAX_TTL` (default 90 days) |

Only `sha256(token)` is stored in the database.

### 5.2 Access token cookie
| Attribute | Value |
|---|---|
| Name | `ca_access` |
| Value | JWT, ES256 |
| Scope | `Domain={COOKIE_DOMAIN}` (for example `.example.com`), `Path=/` |
| Flags | `HttpOnly`, `Secure` (unless `COOKIE_SECURE=false`), `SameSite=Lax` |
| Lifetime | `ACCESS_TOKEN_TTL` (default 15 min) |

### 5.3 JWT claims
```json
{
  "iss": "https://auth.example.com",
  "sub": "<user id>",
  "email": "me@example.com",
  "name": "Display Name",
  "apps": { "recipes": ["admin"], "budget": ["member"] },
  "iat": 1730000000,
  "exp": 1730000900,
  "jti": "<random>"
}
```
- The header MUST include a `kid` that matches a key in JWKS.
- Apps MUST check the signature, `iss`, `exp`, and that their own slug is in `apps`.

### 5.4 Signing keys
- An ES256 private key is loaded from SSM in prod, or from `SIGNING_KEY_PATH` / auto-generated into `.dev-keys/` locally.
- `GET /.well-known/jwks.json` returns the active public key plus any keys listed in `SIGNING_KEYS_RETIRED`, so keys can be rotated without downtime. Cache header: `max-age=3600`.
- A documented manual rotation procedure in `docs/operations.md` is enough. Automated rotation is not required.

## 6. HTTP API

All JSON errors use the shape `{"error": {"code": "snake_case_code", "message": "Human readable"}}`.

### 6.1 Public / browser endpoints
| Method | Path | Description |
|---|---|---|
| GET | `/` | Signed-in status page, or a link to log in |
| GET | `/login` | Login form, or an immediate redirect if a session exists (§4.1) |
| POST | `/login` | Form post (`application/x-www-form-urlencoded`) |
| POST | `/logout` | §4.4 |
| GET | `/setup` | Set-password form (`?token=`) |
| POST | `/setup` | Set the password |
| POST | `/api/session/refresh` | §4.3 (CORS) |
| GET | `/api/me` | The current user's claims as JSON if the session is valid, otherwise `401` (CORS). For static SPAs with no backend. |
| GET | `/.well-known/jwks.json` | Public keys |
| GET | `/health` | `200 {"status":"ok"}`. Checks database connectivity. |

**CSRF:** state-changing POSTs MUST reject requests whose `Origin` header (or `Referer` if `Origin` is missing) is not the auth host or a registered app origin. Together with `SameSite=Lax`, this is enough for the MVP.

**Login errors:** a wrong password, an unknown email, and a disabled account MUST all produce the same generic message ("Invalid email or password").

### 6.2 Admin API
Requires `Authorization: Bearer <ADMIN_API_KEY>`. The service stores only `sha256(key)` and compares in constant time. All endpoints return JSON.

| Method | Path | Description |
|---|---|---|
| GET | `/admin/apps` | List apps |
| POST | `/admin/apps` | Create `{slug, name, origins[]}` |
| GET | `/admin/apps/:slug` | Get one |
| PATCH | `/admin/apps/:slug` | Update `name` / `origins` |
| DELETE | `/admin/apps/:slug` | Delete the app and remove its grants from all users |
| GET | `/admin/users` | List users (optional `?app=slug` filter) |
| POST | `/admin/users` | Create `{email, name?, grants?: {slug: roles[]}}` → returns the user and a **setup link** |
| GET | `/admin/users/:id` | Get one, including grants and active session count |
| PATCH | `/admin/users/:id` | Update `name` / `status` (setting `disabled` revokes all sessions) |
| DELETE | `/admin/users/:id` | Delete the user, their sessions, and their invites |
| POST | `/admin/users/:id/reset` | Create a reset invite → returns a **reset link** |
| PUT | `/admin/users/:id/grants/:slug` | Set roles `{roles: []}` (create or replace) |
| DELETE | `/admin/users/:id/grants/:slug` | Remove a grant |
| DELETE | `/admin/users/:id/sessions` | Revoke all of a user's sessions |
| POST | `/admin/tokens` | **Dev only.** Mint an access token `{user_id or email, ttl?}` for app testing. MUST return `404` unless `ALLOW_TOKEN_MINT=true`. |

`:id` MAY also accept an email address, for convenience in the CLI.

## 7. Data Model (MongoDB)

Database name comes from config (default `clang_auth`).

**`users`**
```
_id: ObjectId
email: string            // lowercased, unique index
name: string | null
password_hash: string | null   // null until setup completes
status: "active" | "disabled"
grants: [{ app: string, roles: [string], granted_at: Date }]  // embedded; small and bounded
created_at, updated_at: Date
```

**`apps`**
```
_id: string (slug, ^[a-z0-9-]{2,32}$)
name: string
origins: [string]        // normalized origins; index for lookup
created_at, updated_at: Date
```

**`sessions`**
```
_id: string              // sha256(token), hex
user_id: ObjectId        // index
created_at: Date
expires_at: Date         // TTL index
absolute_expires_at: Date
last_used_at: Date
user_agent: string | null
ip: string | null
```

**`invites`**
```
_id: string              // sha256(token), hex
user_id: ObjectId        // index
purpose: "setup" | "reset"
expires_at: Date         // TTL index
used_at: Date | null
```

**`login_attempts`** (for rate limiting)
```
_id: string              // e.g. "email:<email>" or "ip:<ip>"
count: number
expires_at: Date         // TTL index
```

Indexes MUST be created on startup in an idempotent way, or with an explicit `migrate` command.

## 8. Admin CLI

Binary name: `clang-auth`. Configured with env vars `CLANG_AUTH_URL` and `CLANG_AUTH_ADMIN_KEY`, or with `~/.config/clang-auth/config.toml`. Output is human-readable by default, and `--json` gives machine-readable output.

```
clang-auth app list
clang-auth app create <slug> --name <name> --origin <url> [--origin <url>...]
clang-auth app update <slug> [--name ..] [--add-origin ..] [--remove-origin ..]
clang-auth app delete <slug> [--yes]

clang-auth user list [--app <slug>]
clang-auth user create <email> [--name ..] [--grant <slug>[:role,role]]...   # prints setup link
clang-auth user show <email|id>
clang-auth user disable <email|id>
clang-auth user enable <email|id>
clang-auth user delete <email|id> [--yes]
clang-auth user reset <email|id>                                            # prints reset link

clang-auth grant set <email|id> <slug> [--role <role>]...
clang-auth grant remove <email|id> <slug>

clang-auth session revoke <email|id>

clang-auth token mint <email|id> [--ttl 1h]      # dev only (requires ALLOW_TOKEN_MINT on server)
```

Destructive commands ask for confirmation unless `--yes` is passed.

## 10. Local Development

### 10.1 The service
- `docker compose up -d` starts MongoDB.
- `cargo run -p service` (or a `make dev` / `just dev` target) serves on `http://auth.localtest.me:4000`.
  - `*.localtest.me` resolves to `127.0.0.1`, so the cookie domain `.localtest.me` works across "subdomains" locally with no `/etc/hosts` edits.
  - The dev config uses `COOKIE_SECURE=false`, `ALLOW_INSECURE_ORIGINS=true`, `ALLOW_TOKEN_MINT=true`, and an auto-generated signing key.
- A committed `.env.example` contains working local defaults.
- A **seed** command (script or CLI subcommand) is idempotent and creates:
  - the app `demo` with origin `http://demo.localtest.me:3000`,
  - the user `dev@localtest.me` with password `devpassword123` and grant `demo: ["admin"]`,
  - a known local admin key (documented in the README).

### 10.2 Apps that use the service
- `examples/node-app` is a minimal TypeScript server (Express or Hono) on `http://demo.localtest.me:3000` that:
  - verifies `ca_access` with `jose` against `${AUTH_BASE_URL}/.well-known/jwks.json`,
  - redirects to login when the token is missing or expired,
  - returns `403` when the user has no `demo` grant,
  - shows the current user and a logout button.
- `docs/integration-guide.md` (§12) explains to new apps:
  - which config to expose (`AUTH_BASE_URL`, `AUTH_APP_SLUG`, JWKS URL),
  - a copy-pasteable verification middleware of about 30 lines,
  - **how to test an app without running the auth service**: make the JWKS URL and issuer configurable, generate a throwaway ES256 keypair in test setup, and sign tokens with the same claim shape (§5.3),
  - how to test an app against a local auth service: `clang-auth token mint`, or the seed user.

## 11. Non-Functional Requirements

### Security
- Argon2id parameters are configurable, with minimums as in §2. Password comparison MUST use the library's constant-time verify.
- **Rate limiting:** after 5 failed logins per email or 20 per IP within 15 minutes, further login attempts for that key return the generic failure until the window expires. Successful logins are not counted. Rate-limited responses MUST NOT reveal whether the account exists.
- Passwords, tokens, invite links, session IDs, and the admin key MUST NEVER be logged.
- Security headers on HTML responses: `Content-Security-Policy` (no inline scripts), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` (keeps invite tokens out of referrers), `Cache-Control: no-store` on auth pages.
- API Gateway throttling and Lambda reserved concurrency MUST be set as described in §11 Cost guardrails.

### Performance (targets, not hard requirements)
- Warm p95: under 50 ms for JWKS, refresh, and admin reads. Under 500 ms for login (Argon2 dominates).
- Cold start under 500 ms including the MongoDB connection.
- The MongoDB client MUST be created once per Lambda container and reused across invocations.

### Cost
**Budget:** expected under $1/month. The hard ceiling is $25/month, even if someone sends abusive traffic all month.

Traffic is low by design. Apps verify JWTs locally, so the auth service only handles logins, refreshes (about one per user every 15 minutes while they're active), JWKS fetches (cached for 1 hour), and admin calls.

**Expected monthly cost (us-east-1, up to about 100k requests/month):**
| Item | Cost |
|---|---|
| Lambda (arm64, 512 MB): 1M requests + 400k GB-s per month are *always free* | $0 |
| API Gateway HTTP API at $1.00/M requests (free for the first 12 months on legacy accounts) | ~$0.10 |
| Route 53 hosted zone (alias queries to API Gateway are free) | $0.50 |
| ACM certificate, API Gateway custom domain | $0 |
| SSM Parameter Store, standard tier, encrypted with the AWS-managed `aws/ssm` key | $0 |
| CloudWatch Logs (5 GB ingest free, 14-day retention) | ~$0 |
| S3 bucket for SAM deployment artifacts | ~$0.01 |
| MongoDB Atlas M0 | $0 |
| **Total** | **≈ $0.60** |

**Cost guardrails (MUST be in the SAM template / `docs/operations.md`):**
- **API Gateway stage throttling:** steady rate **5 rps**, burst **10**. In the worst case, sustained maximum traffic for a whole month is about 13M requests, which comes to about $13 for API Gateway plus about $5 for Lambda and logs. That keeps the worst case under $25.
- **Lambda reserved concurrency: 5.** This limits both compute spend and the number of MongoDB connections (Atlas M0 allows 500 connections and about 100 operations per second).
- **Lambda timeout 10 s.** Memory 512 MB, and `docs/operations.md` MAY suggest tuning it.
- **Explicit `AWS::Logs::LogGroup` with `RetentionInDays: 14`.** Without one, Lambda creates log groups that never expire. Log level defaults to `info`, and request and response bodies are never logged.
- **Forbidden resources:** VPC or Lambda-in-VPC, NAT Gateway, Elastic or public IPv4 addresses, provisioned concurrency, CloudFront, WAF, Secrets Manager, customer-managed KMS keys, X-Ray tracing, CloudWatch dashboards and custom metrics, and REST API (v1) Gateway. Each of these has a fixed monthly cost or a higher per-request price.
- **`docs/operations.md` setup steps MUST include:**
  1. Create an **AWS Budget** with email alerts at $5 actual, $10 actual, and $20 forecasted. The first two budgets are free.
  2. Enable **Cost Anomaly Detection**, which is free.
  3. A **kill switch**: one command that sets the stage throttle to 0, or Lambda reserved concurrency to 0, if an attack shows up.

  Budgets only alert. AWS has no automatic hard spending cap, so the throttle and concurrency limits above are what actually bound the bill.
- **Atlas:** use the **M0 free cluster** only. Not Flex, not Dedicated, and no paid backups or other add-ons.
- **Known trade-off:** Lambda without a VPC has no static IP, so the Atlas M0 IP allowlist must be `0.0.0.0/0`. That is acceptable with a strong, scoped DB user and TLS. Avoiding it would need a NAT Gateway, which costs about $32/month and is forbidden above.

### Observability
- Structured JSON logs to CloudWatch with a request ID. Log group retention: 14 days.
- Audit log lines (level `info`, event name in a field) for: login success and failure, logout, invite created and used, and every admin mutation.

### Deployment
- `sam build && sam deploy` (with a `samconfig.toml`) deploys everything: Lambda, HTTP API, custom domain mapping, log group, and IAM for reading SSM parameters.
- The ACM certificate and Route 53 hosted zone MAY be passed in as parameters instead of being created by the stack.
- `docs/operations.md` (§12) documents first-time setup end to end: Atlas, SSM parameters, generating the signing key, generating the admin key and its hash, deploying, the DNS record, and creating the first app and user.

## 14. Experiment Rules

To keep the two implementations comparable:

1. **This spec is read-only during implementation.** If something is ambiguous, the implementer decides, writes the decision and the reasoning in `DECISIONS.md`, and keeps going. Spec changes happen only between runs and apply to both projects.
2. **Same starting prompt.** Each harness gets the same initial instruction: *"Implement the service described in SPEC.md. Work until the acceptance checklist in §15 passes."*
3. **Human interventions are logged.** Every time the human has to step in (to unblock, correct, or approve something beyond routine tool permissions), add a line to `INTERVENTIONS.md`: timestamp, what happened, and why.
4. **No sharing between projects.** No code or knowledge from one implementation is fed to the other.
5. **Metrics to record at the end** (in `RESULTS.md`):
   - wall-clock time, and token usage or cost as reported by the harness,
   - number of human interventions,
   - acceptance checklist pass rate (§15),
   - test count and whether `cargo test` passes cleanly,
   - `cargo clippy -- -D warnings` result,
   - Lambda binary size, and measured cold and warm latency for `/login` and `/.well-known/jwks.json`,
   - lines of code (`tokei`), excluding generated files,

## 15. Acceptance Checklist

Each item MUST be covered by an automated test (unit, integration against a real MongoDB in Docker or testcontainers, or end-to-end over HTTP), unless it is marked *(manual)*.

**Auth flow**
- [ ] Valid credentials and a registered `redirect_uri` → `302` to `redirect_uri`, with both cookies set and their attributes as in §5.
- [ ] Wrong password, unknown email, and disabled user all → the same generic error. No cookies set.
- [ ] A `redirect_uri` with an unregistered origin, a lookalike host (`example.com.evil.com`), a scheme-relative URL (`//evil.com`), or a `javascript:` URL → never redirected to; falls back to `/`.
- [ ] `/login` with a valid session → immediate redirect with a fresh access token, and no form shown.
- [ ] A user with no grant for the target app → "no access" page, and no redirect.
- [ ] `POST /api/session/refresh` from a registered origin → `200`, a new cookie, and correct CORS headers. From an unregistered origin → no CORS allow headers.
- [ ] Expired or revoked session, or disabled user → refresh returns `401` and clears the cookies.
- [ ] Logout deletes the session, and that session cookie no longer works.
- [ ] A POST with a foreign `Origin` is rejected.
- [ ] The 6th failed login within the window is rate-limited, even with the correct password.

**Tokens**

- [ ] A token signed by a retired key still verifies while that key is listed. A token signed by an unknown key fails.

**Invites**
- [ ] Creating a user returns a setup link. Setting a password through it logs the user in.
- [ ] An invite is single-use, expires, and is invalidated by a newer invite.
- [ ] A reset revokes the user's existing sessions.
- [ ] Passwords shorter than 12 characters are rejected.
